# MARA Stock Terminal — UI/UX Upgrade Implementation Brief

Implement the supplied UI/UX upgrade plan in three controlled phases. Treat this as an incremental refinement of the existing application, not a redesign or rewrite.

## 1. Mandatory safeguards

- Inspect the existing architecture, shared components, design tokens, routing, and current implementations before editing.
- Preserve all existing working features, routes, keyboard shortcuts, market-data integrations, API contracts, caching behavior, refresh intervals, and authentication.
- Do not modify backend refresh logic, environment variables, secrets, API endpoints, or deployment configuration as part of this UI task.
- Do not replace real market data with mock data or hardcoded values.
- Avoid introducing new dependencies unless a clear technical need is demonstrated.
- Reuse existing components and design tokens where possible. Avoid duplicate CSS rules, one-off styling hacks, and unnecessary component rewrites.

## 2. Phase 1 — Visual hierarchy and accessibility

- Audit actual text/background contrast combinations against WCAG 2.2 AA requirements.
- Target at least 4.5:1 for normal text and 3:1 for large text. Check meaningful graphical elements and controls against applicable non-text contrast requirements.
- Improve readability without sacrificing the compact, professional financial-terminal aesthetic.
- Replace ambiguous missing-value em-dashes only where doing so improves clarity. Distinguish market closure, unavailable values, stale data, confirmed delayed data, loading states, and legitimate zero values accurately.
- Improve table and Watchlist row spacing modestly without compromising information density or causing avoidable overflow.
- Preserve alignment of numerical columns, timestamps, and price changes.

## 3. Phase 2 — Interaction polish

- Convert plain-text Analyze actions into appropriately sized ghost buttons or subtle action controls with hover, focus-visible, active, and disabled states.
- Improve Ctrl+K command palette discoverability using a responsive hint such as "Search securities, sectors, macros or commands..." with the correct platform-specific shortcut.
- Preserve existing keyboard navigation, focus management, and command execution.
- Improve empty and error states with concise explanations and truthful last-update information where available.
- Offer fallback actions only when they are implemented and functional. Do not fabricate recovery times, feed availability, or data freshness.

## 4. Phase 3 — Responsive layout and heatmap

- Test cross-asset grids and sector matrices at narrower desktop widths and browser zoom levels.
- Prefer responsive column sizing, sensible minimum widths, and localized horizontal scrolling over page-wide overflow.
- Ensure important labels and controls remain accessible on smaller viewports.
- Add restrained transitions and clear selected/focus states to heatmap cells.
- Respect reduced-motion preferences.
- Keep loading, empty, error, and successful constituent-breadth states visually distinct.

## 5. Execution process

For each phase:

1. Identify the relevant files and summarize the intended changes.
2. Implement only that phase.
3. Run the available lint, type-check, unit-test, and production-build commands.
4. Check for regressions in existing functionality and responsive layouts.
5. Report changed files, tests performed, remaining issues, and any manual verification required.

Do not proceed with a broad rewrite if an isolated component-level change is sufficient. Do not claim visual, accessibility, or functional verification unless it was actually performed.

Start with Phase 1. Keep the diff focused and preserve the existing working application.
