# URGENT: Persistent CSP `script-src` Blocked Error — Root-Cause Debugging

The Content Security Policy error remains after the previous attempted fix. Do not repeat the same changes or apply another speculative workaround.

## 1. Reproduce and Identify the Exact Failure

Open the affected page and reproduce the error.

Collect the following:
- The complete console error, including the script URL, line number, and stack trace.
- Whether the violation is `blocked-uri: eval` or another blocked resource.
- Whether the error occurs on localhost, the production Vercel deployment, or both.
- Whether the error originates from our application, a third-party library, a browser extension, or a development tool.

Do not assume the CSP violation is caused by our own source code.

## 2. Inspect the Effective CSP

Inspect the actual HTTP response headers for the main HTML document in DevTools → Network → document request → Headers.

Check:
- Every enforced `Content-Security-Policy` header.
- Any `Content-Security-Policy-Report-Only` header.
- Any CSP `<meta>` tag in the HTML.
- Whether Vercel deployment configuration, middleware, a proxy, or hosting configuration adds another policy.
- Whether the policy differs between localhost and production.

Remember: multiple enforced CSP policies are applied together. A more permissive policy does not override a restrictive one.

## 3. Trace the Exact Offending Script

Search the application source and dependency code for:
- `eval(`
- `new Function(`
- String-based `setTimeout` and `setInterval`
- Libraries or plugins that dynamically compile JavaScript.

Use the stack trace and source maps to identify the actual caller. Inspect package scripts, bundler configuration, and dependency versions where relevant.

Do not assume that finding one occurrence proves it caused this violation.

## 4. Apply a Root-Cause-Specific Fix

Choose the fix only after identifying the responsible code:

- **Application code:** replace dynamic string evaluation with ordinary functions or callbacks.
- **Third-party dependency:** update, replace, or configure the dependency to avoid dynamic evaluation.
- **Development-only tool:** correct the development configuration without weakening production security.
- **Incorrect CSP configuration:** correct the actual policy source and preserve the remaining security directives.
- **Browser extension:** verify in a clean browser profile before changing application code.

Do not add `'unsafe-eval'`, disable CSP, or weaken other security directives merely to silence the warning.

## 5. Verify the Actual Result

After making the fix:

1. Run the production build.
2. Start the application and reproduce the original error.
3. Check the console again after a clean reload.
4. Verify the effective CSP headers on the deployed site.
5. Test the affected UI and relevant API requests.
6. Confirm that the original violation is gone, rather than simply hidden or converted into a report-only warning.

## 6. Report Back With Evidence

Return:
- **Root cause:** the exact file, library, or configuration responsible.
- **Evidence:** the relevant console stack trace and CSP directive.
- **Changes:** exact files modified and what changed.
- **Verification:** build results and whether the issue is resolved locally and in production.
- **Remaining issues:** anything that could not be reproduced or verified.

If evidence is insufficient, stop and request the missing diagnostic information instead of making additional speculative changes.

**Definition of done:** The original CSP violation is resolved through a verified fix, the security policy remains appropriately restrictive, and the application's functionality continues to work.
