# MARA STOCK DASHBOARD — NSE PROVIDER ACCESS FAILURE & MARKET DATA RELIABILITY

## Incident Classification
Production Backend — External Data Provider Failure

## Objective

Investigate and resolve widespread NSE API HTTP 403 failures observed in Vercel production logs.

The objective is to restore reliable Indian market data retrieval, eliminate unnecessary upstream requests, and improve provider resilience without compromising the existing architecture.

## 1. Investigate NSE Provider Failure

Inspect the existing NSE provider implementation.

Determine why production requests receive HTTP 403.

Investigate:

1. Whether NSE is blocking requests originating from the production hosting environment.
2. Whether the provider requires an active session or valid cookies.
3. Whether request headers and session initialization follow the provider's documented access requirements.
4. Whether the provider has introduced endpoint or access-policy changes.
5. Whether request frequency is triggering automated traffic restrictions.
6. Whether the production environment behaves differently from local development.
7. Whether the current implementation depends on unofficial NSE endpoints.

Inspect response headers and a safely captured response body where possible.

Do not assume that adding browser User-Agent headers alone will solve the problem.

Do not repeatedly retry HTTP 403 responses.

Do not attempt to bypass provider access restrictions through rotating proxies, IP rotation, or other access-control evasion.

## 2. Investigate Excessive Request Volume

The `/api/analytics/sectors` endpoint appears to trigger requests for many individual NSE constituents within approximately seven seconds.

Investigate:

- How many upstream requests are generated per sector request.
- Whether multiple requests for the same symbol happen simultaneously.
- Whether requests are unnecessarily repeated across users or dashboard refreshes.
- Whether requests are sequential or concurrent.
- Whether the existing cache is being bypassed.
- Whether multiple frontend components independently trigger the same analytics request.

### Required improvements

- Implement request deduplication.
- Use shared caching for sector constituents.
- Introduce appropriate TTL policies.
- Apply concurrency limits.
- Prevent duplicate upstream calls.
- Avoid retry storms.
- Use batch endpoints only where officially supported.
- Implement provider circuit breakers.

A single sector dashboard refresh should not create uncontrolled upstream traffic.

## 3. Review Market Data Provider Architecture

Inspect existing provider abstractions and Core Contracts.

Determine whether the application can use alternative legitimate market-data providers when NSE becomes unavailable.

Evaluate existing integrations before introducing new dependencies.

Requirements:

- Support provider fallback where compatible.
- Maintain consistent symbol normalization.
- Preserve source attribution.
- Track data timestamps and freshness.
- Distinguish live, delayed, cached, and unavailable data.
- Validate provider capabilities before requesting data.
- Avoid silently mixing incompatible datasets.

Do not replace the entire market-data architecture.

Do not introduce a new provider without evaluating its availability, API limits, terms, and compatibility.

## 4. Fix Yahoo Finance Symbol Resolution Separately

Production logs contain:

`HTTP Error 404: Quote not found for symbol: TATAMOTORS.NS`

Investigate:

- Whether the symbol is valid for the requested historical period.
- Whether the company has undergone a corporate action or symbol transition.
- Whether the instrument mapping is outdated.
- Whether Yahoo Finance supports the requested endpoint for this instrument.
- Whether the provider response is being incorrectly classified.

Implement proper handling for unavailable or changed symbols.

Do not fabricate market data or substitute another instrument without validation.

## 5. Improve Error Classification

Create consistent provider error handling.

Distinguish between:

- 400 — Invalid request.
- 401/403 — Authentication or access restriction.
- 404 — Instrument or resource not found.
- 429 — Rate limit exceeded.
- 500 — Provider/internal server failure.
- 502/503/504 — Upstream or service availability failure.

Requirements:

- Do not retry permanent 403 or 404 failures blindly.
- Apply exponential backoff and jitter to retryable failures.
- Respect Retry-After headers.
- Use circuit breakers for repeatedly failing providers.
- Preserve last-known-good cached data where appropriate.
- Expose structured internal diagnostics.
- Never log API credentials, session cookies, or sensitive headers.

## 6. Frontend Data Reliability

Ensure sector analytics remain usable when NSE is unavailable.

Expected behavior:

- Display cached sector data when available.
- Clearly identify stale or delayed data.
- Show provider availability status.
- Avoid displaying stale data as live.
- Show partial results when only some constituents are available.
- Provide a graceful unavailable state when no reliable data exists.

Do not allow one provider failure to break the entire Markets workspace.

## 7. Testing Requirements

Test:

1. NSE HTTP 403 handling.
2. NSE temporary outage handling.
3. Provider HTTP 429 handling.
4. Yahoo Finance 404 handling.
5. Sector analytics with cached data.
6. Sector analytics without cached data.
7. Concurrent requests for identical symbols.
8. Repeated dashboard refreshes.
9. Provider fallback behavior.
10. Data freshness and source attribution.

Verify that the solution works in the production hosting environment, not just locally.

## 8. Final Report

Provide:

- Confirmed root cause of NSE 403 responses.
- Whether the problem is hosting/IP-related, session-related, rate-related, or policy-related.
- Exact upstream request volume before and after optimization.
- Cache and deduplication improvements.
- Provider fallback strategy.
- Yahoo Finance symbol-resolution findings.
- Files modified.
- Tests executed.
- Production deployment verification.
- Remaining provider limitations.

## Execution Strategy

INVESTIGATE → TRACE REQUESTS → CONFIRM PROVIDER FAILURE → REDUCE REQUEST VOLUME → IMPLEMENT RESILIENCE → TEST → DEPLOY → VERIFY.

### Critical constraints

Preserve the existing architecture.

Do not fake market data.

Do not disguise provider failures as successful responses.

Do not blindly increase retries.

Do not bypass external provider access restrictions.

Prioritize data correctness, provider independence, caching efficiency, and production reliability.

The final objective is to make Mara resilient to individual market-data provider failures without compromising the accuracy of its financial information.
